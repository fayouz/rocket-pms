Rocket PMS fonctionne seul (comptes locaux, LDAP) ou **dans la suite Rocket** : la connexion passe alors par Rocket Auth, le menu propose le sélecteur des applications et la déconnexion est propagée à toutes les applications.

## Environnement complet

`compose.suite.yaml` lance, pour une démo locale uniquement (mots de passe et secrets connus) :

| Application | Adresse |
|---|---|
| Rocket Auth | http://localhost:3100 |
| Rocket Cloud | http://localhost:3200 |
| Rocket PMS | http://localhost:3700 |
| Rocket Place | http://localhost:3900 |

Rocket Auth et Rocket Cloud sont construits depuis les dépôts voisins de rocket-middlewares (`ROCKET_AUTH_DIR`, `ROCKET_CLOUD_DIR`, par défaut `../../rocket-middleware/rocket-<brique>`), Rocket Place depuis `ROCKET_PLACE_DIR` (par défaut `../rocket-place`).

```bash
docker compose -f compose.suite.yaml up -d --build
```

Connectez-vous avec un compte de démo de Rocket Auth (annuaire LDAP de démo, groupe `rocket-admins` administrateur).

## Appels entre applications

Aucun jeton statique : chaque application obtient un jeton de Rocket Auth (*client credentials*) pour l'application appelée.

- Rocket PMS → Rocket Place : audience `rocket-place`.
- Rocket Place → Rocket Cloud (documents) : audience `rocket-cloud`.

L'application appelée accepte le jeton si un administrateur a lié une application au client appelant (Administration → Applications, champ « Client Rocket Auth ») ; dans cet environnement, le service `suite-link` le fait. Hors suite, `ROCKET_PLACE_TOKEN` et `ROCKET_CLOUD_TOKEN` restent utilisés.

## Variables

`ROCKET_AUTH_URL` (vide : mode autonome), `ROCKET_AUTH_INTERNAL_URL`, `ROCKET_AUTH_CLIENT_ID`, `ROCKET_AUTH_CLIENT_SECRET`, `ROCKET_AUTH_ADMIN_GROUP`, `ROCKET_PUBLIC_URL`, `ROCKET_INTERNAL_URL`.
